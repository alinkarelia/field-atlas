# Данные, измерения и передача

## Раздельные проекты

`project.type` принимает `interior`, `exterior`, `land`, `cemetery`. Объекты, файлы и фрагменты принадлежат одному проекту. Сервер не позволяет перенести ID объекта или файла в другой проект и не собирает фрагменты разных проектов. Карточка `grave` допустима только в кладбище.

Основные объекты карты: `boundary`, `road`, `path`, `grave`, `tree`, `dump`, `obstacle`, `anomaly`, `entrance`, `object`, `room`, `facade`. Пауза/потеря GPS создаёт отдельный отрезок. Контур с разрывом нельзя автоматически замкнуть и объявить проверенной границей.

## Системы координат

Местный план использует метры от `GeoOrigin(lat,lon)`. Это приближение для локального участка, не геодезическая сеть. Нативная съёмка хранит AR-мировые координаты в порядке `[worldX, worldZ, worldY, confidence]`; третья координата — высота. Каждый независимый запуск получает собственный `frameId`. GPS не делает два AR-пространства одинаковыми.

Фрагмент `field-scan-v1` содержит `id`, `frameId`, `tracking`, `points`, `anchors` и, у нативного клиента, `sourceFrameIds`. Допустимое качество точки — 0, 1, 2. Отсутствие точки означает отсутствие измерения; пустые зоны не закрашиваются автоматически.

Сервер совмещает части общей системы координат либо по минимум трём одинаково названным, пространственно разнесённым опорным точкам. Используется жёсткое преобразование Kabsch без изменения масштаба. Невязка ограничена; неподходящие/коллинеарные ориентиры отклоняются. Допуск невязки не является заявлением о точности всего LiDAR. Независимые фрагменты без ориентиров не приклеиваются по близости GPS.

## Фрагменты и производные данные

Нативный код сбрасывает накопление примерно по 20 тысяч точек; исходные выбранные depth/confidence/RGB-кадры записываются отдельно примерно раз в 4 секунды. Это выбранные калиброванные кадры, а не запись каждого кадра сенсора. Бинарные глубины хранят размер/stride, intrinsics, timestamp, transform и ссылки на RGB/confidence.

При передаче файл имеет устойчивый ID, длину и SHA-256. Клиент спрашивает подтверждённое смещение, передаёт блоки, затем завершает загрузку. Сервер считает файл принятым только после проверки хеша; исходники не удаляются по таймеру. Повтор запроса изменения карточки имеет ID и ожидаемую версию. Конфликт не перезаписывает серверные сведения.

Новый путь `POST /api/assembly-jobs` принимает 1–2000 фрагментов до 40 МБ каждый. Повтор одинакового набора ID возвращает то же задание. Статус хранится в SQLite; сервер работает независимо от открытого диалога, а клиент восстанавливает проверку статуса. После перезапуска незавершённое задание получает состояние для повторной попытки. Тяжёлый этап исполняется по одному, очередь ограничена 64 заданиями. Отмена не удаляет исходники и не публикует недостроенную модель.

Исходники читаются по одному. Дедупликация производных точек по ячейке 10 см использует дисковую временную SQLite; оригиналы остаются неизменными. Итоговые данные публикуются после готовности всех файлов, временная база удаляется. Это полная повторная сборка выбранного набора, не инкрементальное добавление к прежней модели. В испытании проверены 45 фрагментов; максимум 2000 является программным ограничением, а не подтверждённым нагрузочным результатом.

Результат разбит на сектора 10 × 10 м. Каждый сектор имеет обзор, полное покрытие, bounds и страницы по 10 000 производных точек. Общий обзор распределён по всем секторам и ограничен примерно 30 тысячами точек. Крупный сектор нельзя случайно скачать через старый маршрут одним чрезмерно большим JSON. 3D-интерфейс даёт выбор любого сектора и каждой его страницы; 12 последних открытых ответов кешируются для офлайн-просмотра. Кеш просмотра не считается резервной копией оригиналов.

Индекс содержит преобразования, принятые/спорные части и обзор покрытия до 50 тысяч ячеек; полное покрытие каждого сектора доступно отдельно. Отсутствующие измерения не дорисовываются. Старый синхронный `/api/assemble` с пределом 40 оставлен для совместимости; текущие браузерный и нативный исходные клиенты используют фоновое задание.

Ещё нужны проверка на больших реальных экспедициях, инкрементальная сборка, геопривязка и пространственная загрузка ближайших частей непосредственно в AR на телефоне. Локальный HTTP/SQLite-сервер остаётся песочницей.

## x0

Серверный адаптер использует контракт `archive-analysis-v1` существующего OCR-сервиса x0: изображение → текст и области текста. Проверяются хеш нормализованного PNG, форма ответа и координаты областей. Сохраняется хеш исходного фото. PNG для OCR является производной копией; файл оригинала не заменяется.

Результат не меняет ручной текст без нажатия «Вставить предложенный текст». При замене фотографии результат старого фото не принимается. Неполные даты и сомнительные чтения должны оставаться видимыми. Исправление, которого нет в источнике, не должно превращаться в биографический факт.

Этот адаптер пока использует обычный OCR x0. Более сложное задание `archive.transcribe`, многокадровый анализ бокового освещения, RTI, фотограмметрия и чтение микрорельефа ещё не реализованы.

## Проверка перед первой полевой работой

Сначала собрать iOS и проверить разрешения камеры/геолокации, совместимость MapLibre, поворот экрана и большие шрифты. Затем на измеренном участке: сравнить рулетку и AR, проверить дрейф, солнце/тень/блики, разрывы и повторную локализацию, нехватку памяти/диска, уход приложения в фон, принудительное завершение и восстановление. Отдельно проверить реально недоступную сеть и возобновление больших файлов.

До этих испытаний исходники iOS нельзя считать полевым релизом. Карточки и фото в песочнице проверены, точность сенсора и сохранность при всех iOS-сценариях жизненного цикла пока не измерены.

## Планы помещений

`roomPlan` разрешён только для `room` в проекте `interior`. Контракт, размерные линии, профиль стены, этажи и независимые группы координат описаны в [ROOM-PLANS.md](ROOM-PLANS.md). Номер этажа можно исправить без замены источника. Подсказка барометра не является измерением потолка или автоматической привязкой комнат.
