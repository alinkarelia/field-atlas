# Люди, захоронения и граф связей

Захоронение — объект обследования. Фотография и надпись — источники. Человек в архиве — самостоятельная сущность. Несколько людей могут быть указаны на одном памятнике; один человек может упоминаться на нескольких памятниках. Надпись на мемориале сама по себе не доказывает место фактического погребения.

Поэтому реализованное ребро называется `inscription_refers_to`: «этот человек упомянут в этой надписи». Его узлы — `recordId + slot` и `source + personId`. Отдельная подтверждённая связь места погребения может быть добавлена после проверки источников. Идентификаторы карточек и фотографии сохраняются.

## Работающий обмен

`POST /api/identity/import` принимает `field-people-v1`. Пример: `examples/people.json`. Обязательные поля: `source`, `people[].id`, `people[].name`; остальные текстовые: `birth`, `death`, `place`, `url`. Один файл — до 2 МБ и 5000 карточек; импорт дополняет/обновляет локальную копию и не удаляет отсутствующих людей. Повтор ID внутри файла отклоняется. IDs ограничены ASCII-буквами, цифрами, дефисом и подчёркиванием, длина до 100.

Поле `source` — устойчивое пространство идентификаторов сайта, например `archiverf`. Не используйте одно пространство для разных баз. Ссылка `url` должна вести на доступную карточку по HTTPS. Признак `synthetic: true` обязателен для учебных подборок. Импортировать следует только сведения, которые текущему пользователю разрешено читать и сохранять.

`GET /api/identity/candidates?recordId=...` возвращает варианты по каждому человеку из карточки. Сравнение учитывает части имени, ё/е и часть дореформенных букв, известные даты. Текущая версия не использует родственные связи или географию для рейтинга; место отображается для человека. Неопределённые даты сохраняются буквально, не превращаются в точные годы. Число сортировки не является вероятностью.

`POST /api/identity/decide` принимает `recordId`, `slot`, `personKey`, `token`, `state`, `evidence`. Допустимы `confirmed`, `rejected`, `revoked`. Решение содержит текстовое основание. Повтор того же решения идемпотентен. Противоречащие точные даты/части имени блокируют подтверждение до уточнения источников. Для одной записи человека на плите нельзя одновременно подтвердить две разные карточки людей.

`token` привязан к прочитанным сведениям, исходным фотографиям, месту и версии импортированной карточки человека. При изменении этих сведений старое решение имеет `effectiveState: needs_review`. Изменение только заголовка/служебной версии не сбрасывает связь. Все решения остаются в аудите. Подтверждение не меняет карточку человека.

`GET /api/identity/graph?projectId=...` возвращает `field-graph-v1`: проект, памятники, упомянутые архивные карточки, связи, основания, историю. Экспорт явно содержит `mergePeople: false`. Получатель должен учитывать именно `effectiveState`, а не только историческое `state`, и не трактовать `needs_review` как подтверждение.

## Подключение существующего сайта

В локальном снимке исходников сайта от 18.11.2026 найдены `person_identity.py` и `person_identity_routes.py`: API предварительной проверки `/api/people/identity-preview`, утверждения `/api/person-identity-links`, действия над ними и `/api/people/{pid}/identity-view`. Это механизм тождества **двух карточек людей** с проверкой прав и участников, отрицательными утверждениями и аудитом.

Он не является готовым импортёром захоронений. Нельзя передавать ID захоронения вместо `left_id` человека. Нельзя обходить текущие права сайта прямой записью в его SQLite. Этот снимок — ориентир интеграции, не доказательство состояния работающего сервера.

Следующий этап интеграции на актуальной ветке сайта:

1. Экспорт доступных волонтёру людей с устойчивыми ID, датами и версией. Авторизация, область доступа и удаление доступа должны проверяться на сайте.
2. Приём `field-graph-v1` в промежуточную область проверки. Хранение происхождения `projectId/recordId/slot`, хешей фотографий, версии чтения, автора и времени решения. Повтор импорта не дублирует источник.
3. Создание узла источника и ребра к существующему человеку после проверки полномочий. `local-reviewer` из песочницы не становится пользователем сайта: его нужно заменить подтверждённой сервером личностью.
4. Если действительно найдены две уже существующие карточки человека, использовать действующий процесс `same_person`/`different_person` сайта. Физическое разрушительное слияние и удаление карточек в поле не выполнять.
5. Присылать обратно стабильный ID источника, статус модерации и версию. При изменении или отзыве прав пересматривать доступ и устаревшие предложения.

В этой поставке действующий сайт не изменён; приватные карточки с него не выгружались; авторизация сайта в приложение не встроена. Локальные импорт, предложения и решения проверены тестами, живой обмен с сайтом остаётся отдельным этапом.
